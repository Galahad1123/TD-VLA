# TD-VLA：工程与复现约定

更新日期：2026-11-13。本文是待实施的工程约定，不代表环境、目录、训练或部署已经完成。研究语义见 [research-design.md](research-design.md)，第一版模型范围以 [模型架构设计](model-architecture-v1.md) 为准：第一版不增加 Temporal 历史或模型跨窗口缓存。下文相关缓存与历史验收项仅适用于后续有状态扩展。

## 1. 项目边界

主仓库：[Galahad1123/TD-VLA](https://github.com/Galahad1123/TD-VLA)。采用独立研究包，第一版适配一个 backbone 和 RoboTwin 2.0，避免直接把全部研究逻辑写入上游 fork，也不预先构建通用训练平台。

核心模型不得依赖仿真器。机器人状态、相机信息、成功判定和外部数据格式通过适配层转换。模型、数据标注、评测各自独立，支持以后更换 backbone 或 benchmark。

## 2. 目标目录结构

```text
src/td_vla/
  models/           # backbone 适配、Temporal–Depth 与多头基线
  data/             # 样本读取、时序窗口、预处理和对齐
  annotation/       # 双臂投影、任务阶段规则及校验
  training/         # 训练、损失和恢复
  evaluation/       # 多流指标、结果记录与汇总
  integrations/     # RoboTwin、策略通信与外部运行时适配
configs/            # 模型、数据、训练、实验配置
scripts/            # 数据准备、训练、服务与评测的薄入口
tests/              # 接口、关键计算和小规模集成检查
docs/               # 研究设计、工程约定、复现和贡献指南
external/           # 固定版本的上游代码
pretrained/         # 基础权重与配套元信息
data/               # 数据入口、标注和处理后数据
outputs/            # 训练检查点及恢复元信息
logs/               # 日志、评测、视频和分析
```

配置、来源清单及正式发布报告纳入 Git；第三方工作副本、数据、权重、缓存、日志和检查点默认不直接提交。可在仓库维护小型人工构造测试样本。上游依赖的获取机制待实现时确定，但必须固定提交并记录来源与许可，不能只依赖移动的 main 分支。

## 3. 本机与远端分工

本机负责开发、小样本调试、单元测试和文档。通过 SSH 别名 `F43-6000x2` 访问实验机，由其承担主要数据生成、训练、评测和性能测量。两边通过主仓库同步代码。

2026-11-13 只读检查确认远端有两张 RTX PRO 6000 Blackwell Max-Q，每张约 96 GB 显存，Ubuntu 22.04，驱动 595.71.05，并存在 CUDA 13.0 工具包目录。存在 Miniconda 目录，但非交互 SSH 的 PATH 未找到 Python/Conda；具体运行环境尚未验收。

用户指定根分区存放代码和运行环境，约 1.1 TB 的 `/root/autodl-tmp` 存放大文件。目标布局：

```text
/root/TD-VLA/                    # Git 工作区
/root/TD-VLA/.venv/              # uv 本机/开发环境
/root/TD-VLA/envs/policy/.venv/   # uv 模型环境
/root/TD-VLA/envs/sim/.venv/      # uv 仿真环境
/root/autodl-tmp/td-vla/
  data/
  pretrained/
  outputs/<experiment_id>/
  logs/<experiment_id>/
  cache/
  assets/                       # 仿真资源
```

仓库中的产物入口可用本地软链接指向数据盘，同时支持配置覆盖。机器专用绝对路径不写入共享实验配置。根分区约 30 GB，下载、编译及数据处理缓存应放数据盘；依赖安装前检查剩余空间。

数据盘在实例释放或容器重建后的持久化规则尚未确认，不能将其视为备份；正式检查点、标注规则和结果需要另行归档。

## 4. 环境与下载加速

模型训练/服务与 RoboTwin 仿真分别维护环境，通过现有策略通信方式连接。本地轻量测试尽量不强制安装仿真依赖。双卡训练优先常规数据并行，batch size、混合精度和冻结策略经实际验证后确定。

用户指定的下载优先级：

- Hugging Face 模型和数据优先通过 `hf-mirror.com`，由下载进程的 `HF_ENDPOINT` 等受支持配置指定。
- Python 包及环境依赖优先使用清华 TUNA 镜像中对应的软件源；由 uv 配置 Python 包索引，CUDA wheel 使用显式官方索引，不使用 Conda 管理项目。
- 镜像缺失、不同步或特定 CUDA wheel 需要专用源时，回退官方或项目指定源，并记录实际来源。
- 保留原始模型 ID、精确 revision、文件校验值和软件版本；加速源不改变实验资产身份。
- 认证仍遵循原模型访问要求，不将 token 或凭据写入脚本、配置、日志或仓库。

Hugging Face 缓存、pip 缓存及编译缓存放数据盘，配置在机器环境中。具体镜像地址和客户端兼容性在环境搭建时验证，本文不直接执行全局配置变更。

存在 CUDA 工具包不等于训练环境可用。环境验收需实际验证 Blackwell 上的 PyTorch 运算、所需注意力实现、双卡通信、仿真渲染及策略通信。记录 Python 包锁定信息、驱动、GPU、CUDA 运行时、仿真代码及资源版本。

## 5. TurboVLA 与 RoboTwin 的复用边界

已阅读官方 README、RoboTwin 说明、评测启动脚本、策略客户端和模型包装代码，尚未运行复现。

- 官方 RoboTwin 配置采用三视角输入、14 维双臂绝对关节动作和 50 步 ACT 头。先保留这些约定复现基线。
- 官方评测支持策略服务与仿真分环境部署；复用成功判定、任务启动及动作转换逻辑。
- 上游说明要求评测使用 RoboTwin `bf44be5`，该版本每任务评测 100 个 episode，不能假定 `ROBOTWIN_TEST_NUM` 会改变数量。正式复现记录完整提交号；调试子集与正式结果分开标注。
- 检查点同时保存或关联 `config.yaml`、`dataset_statistics.json` 等配套信息。旧检查点键映射需验证数值一致性。
- 左右关节与夹爪在模型和仿真端的排列不同，适配测试必须覆盖顺序及归一化往返。
- 现有客户端支持执行窗口设置；预测长度与重新请求策略的间隔分开记录。
- TD-VLA 需扩展多流输出的接收、时间戳与日志；有状态 Temporal 模型还需要服务端 episode 重置和并发会话隔离。

核心输出接口必须区分动作、左右 Track、阶段及时间含义，但具体类型和通信字段在模型设计确定后定义。不能只修改服务端返回值而让客户端静默丢弃辅助输出。

## 6. 数据与标注可追溯性

数据记录至少关联任务、episode、采样时间、机器人与相机约定、动作归一化、数据来源及阶段规则版本。派生 Track 与阶段标签应能追溯到原始轨迹，不覆盖原始数据。

按完整轨迹划分训练、验证与测试，避免重叠窗口泄漏；归一化等统计仅从约定的训练集计算。数据划分清单纳入版本管理。区分缺失标注、出画和遮挡；出画与遮挡保留 Track 监督，不能统一当作无效点或有效零坐标。具体以 [Track 与阶段约定](data/p2-annotation-rules.md) 为准。

仿真特权状态与策略可见输入隔离。逐任务检查阶段标注、左右点身份、相机投影、图像变换和时间对齐，生成可人工抽查的视频。先确认原始数据或回放是否提供足够状态，不假定 LeRobot 转换数据包含所有标注所需信息。

## 7. 实验、检查点与日志

每次运行使用唯一 experiment_id，outputs 与 logs 以该 ID 关联：

```text
outputs/<experiment_id>/
  checkpoints/
  config.yaml                   # 完整解析后的配置
  provenance.json               # 代码、数据、资产与环境来源
logs/<experiment_id>/
  train/
  eval/
  analysis/
```

正式实验固定 Git commit，运行期间不原地更新代码。开发使用分支，main 保持可运行；当前文档写入不自动授权推送或合并。脏工作区调试需明确标记，正式结果必须可追溯到确定版本。

记录随机种子、世界大小、全局 batch size、梯度累积、训练步数、精度、耗时及硬件。基础权重记录版本和校验信息。恢复检查点需包含适用的优化器、调度器、随机数、EMA 和训练进度状态；仅推理权重与完整恢复检查点明确区分。

评测保存逐任务和逐 episode 结果、种子、失败原因、执行窗口、预测窗口及模型版本，再生成汇总。不得只保存一个平均成功率。区分模型推理耗时、传输耗时、首个动作可用时间和全部输出时间。

正式分析报告连同复现实验配置纳入版本控制；原始大量日志和视频保留在数据盘。多种子策略与重复实验数量在正式实验协议中确定，不承诺跨硬件逐位一致。

### 任务收尾与产物清理

自 2026-11-14 起，每项任务完成并验证后，必须在汇报前清理本次产生的中间产物、测试输出与不必要日志；双机任务覆盖两端。

- 临时文件使用任务专属目录，验证结束后删除；清理测试缓存、重复标签/叠图、下载分片、重复诊断检查点和已被最终结果替代的日志。
- 保留原始数据、正式检查点、必要配置/来源/校验值、简短验收结果，以及未解决故障的最小证据。测试源码和可复用环境不是临时输出，不随清理删除。
- 清理前确认无相关活跃进程，按已检查的具体路径操作，不对共享数据盘、环境或第三方目录执行泛化递归删除。
- 失效标签应清除派生副本，同时更新文档入口与状态，避免继续引用已删除产物或把旧规则当成当前约定。
- 清理后检查保留数据的完整性和残留；不为了记录清理再生成大量日志，只在任务报告中保留范围、结果及必要例外。

## 8. 分阶段验收与开源交付

1. 官方策略：固定上游与资产版本，跑通原始检查点评测。
2. 适配一致性：相同输入比较动作输出，检查归一化、左右顺序、执行窗口和 reset。
3. 标注数据：少量任务验证投影和阶段规则，通过可视化与时间对齐检查。
4. 多头基线：统一数据和评测，验证损失与输出，记录控制和辅助预测表现。
5. Temporal–Depth：加入真实历史和条件生成，检查未来信息泄漏、跨 episode 状态污染及与基线的公平性。

维护无需完整仿真即可运行的接口和计算测试，以及需要 GPU/仿真的小规模集成检查。训练恢复测试需确认进度与相关状态正确恢复。正式指标前完成预处理和检查点数值一致性验证。

开源提供安装说明、资产获取与版本清单、小规模流程检查、完整训练评测命令和已知限制。明确区分“流程跑通”与“论文指标复现”。保留第三方许可、版权和引用；代码、权重、数据分别检查分发条件。
